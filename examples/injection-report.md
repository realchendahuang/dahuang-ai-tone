# 模型腔调改写报告（示范）

> 展示"加味是改结构/行为模式，不是堆口癖"。同一个原文，加成不同家族/版本的味，每条说明改了什么组织方式。

## 原文

> 这个功能别急着上。用户还没说清楚自己要什么，我们先做会浪费时间。

## 改写示范 1：加 Claude Opus 4.8 味

### 改写后

不建议直接上线。用户需求还没说清楚，先做 3-5 个访谈能更快判断真实优先级，也能避免返工。

### 我加的模型腔

1. **去掉 validation-forward 开场**——原文已经没有"你说得对"之类套话，保持不变；但确认开场直接给观点，符合 Claude 4.8 官方自承的 "minimal validation-forward phrasing"。
2. **第一句直接给观点**——"不建议直接上线"，不加"我会倾向于"这种 hedging，符合 4.8 的 direct/opinionated。
3. **收尾不啰嗦**——不补"希望对你有帮助"或温情升华，符合 4.8 官方自承的 sparing 风格。
4. **emoji 克制**——不加任何 emoji，符合 4.8 官方自承。
5. **没堆"可能/取决于"**——如果只是塞 hedging 词，就会变成 audit-workflow 批评的误判源。

### 边界

这是 Claude 4.8 表面的风格模拟，不代表由 Claude 4.8 生成，也不能从这段反推版本。

---

## 改写示范 2：加 Claude 3.x 味

### 改写后

我会倾向于先不要急着上线这个功能。但这不一定意味着功能本身没有价值，而是说在用户需求还没有被充分说清楚的情况下，直接进入开发可能会带来额外的返工成本。更稳妥的做法，是先明确用户真正想解决的问题。

### 我加的模型腔

1. **开场用"我会倾向于"降低结论强度**——这是 Claude 3.x 的 hedging 模式，区别于 4.8 的 direct。
2. **加"这不一定意味着功能没有价值"**——先保护反方再给限制条件，是 Claude 3.x 的边界表达。
3. **用"更稳妥的做法"给建议**——温和可商量，不命令式。
4. **版本特征是推导**——Claude 3.x 的过度 hedging 是业界共识，4.8 官方自承反向印证，但没有同 prompt 对照样本，标低置信度。
5. **加味靠改整体语气和组织**，不是堆"可能/取决于"——如果只塞 hedging 词，删掉后就不像了，说明加的是口癖不是腔调。

### 边界

这是 Claude 3.x 表面的风格模拟，不代表由 Claude 3.x 生成。Claude 3.x 的 hedging 特征是推导（4.8 官方反向印证），不是硬证据。

## 改写示范 3：加 OpenAI o-series 味

### 改写后

用户需求未明确，直接上线风险高。建议先确认几个问题：目标用户是谁、核心场景是什么、现有流程里这个功能解决哪个痛点。确认后再决定是否排期。

### 我加的模型腔

1. **去掉 markdown 格式，用纯文本段落**——符合 o-series（o1-2024-12-17+）官方默认不输出 markdown 的硬签名。
2. **开头先给澄清问题而不是直接给方案**——符合 OpenAI 官方对 o-series "the planners" 的定性：会主动问澄清问题而不是瞎猜。
3. **不堆"结论是……原因有三点"**——o-series 不是 GPT workhorse，不靠任务化分点。
4. **版本特征是硬证据**——o-series 默认无 markdown 是 OpenAI 官方明文，可以直接引用。

### 边界

这是 o-series 表面的风格模拟，不代表由 o-series 生成。无 markdown 是 o-series 官方签名，但纯文本也可能是其他来源，不能反推。

## 自检：加味有没有变成堆口癖？

  - 示范 2：删掉 hedging 后就变成普通建议，不像 3.x——说明 hedging 是 3.x 的核心特征，但要注意不能只堆词，要改整体组织 ✓（这里 hedging 确实是 3.x 的可观察特征，不是口癖，但加的时候要整段改组织）
